# Karyo WMS - API standards and implemented surface

**Audience:** Integrators and API developers. **Reviewed:** 2026-09-08.
Conventions guide new work; they do not create endpoints, filters or response fields. For an exact
operation, use its JAX-RS resource, API-module DTO and tests. There is no universal query language
or guarantee that every collection has the same shape.

## 1. REST API conventions

- Public routes use `/api/v1/{resource-plural}` in kebab-case; JSON fields use camelCase.
- Domain actions use POST subpaths such as `/delivery-orders/{id}/release`.
- Both desktop and floor PWA use `/api/v1`. There is no `/api/mobile/v1` BFF.
- Internal module calls are injected SPIs or CDI events, not REST. nginx rejects `/api/internal/`.
- `@RolesAllowed` and owner scope are independent checks. The owner comes from authenticated
  context and the operation's attribution contract, not an `X-Tenant-Id` header. See
  [ADR-019](decisions/ADR-019-oauth2-oidc-with-keycloak.md) and
  [ADR-020](decisions/ADR-020-multi-tenancy-strategy.md).
- Send `X-Correlation-Id` to correlate a request with journal entries. It is not generated by
  `TenantFilter` when omitted, and is not an OpenTelemetry trace id.

## 2. HTTP methods and status codes

GET reads; POST creates or performs an action; PUT/PATCH semantics follow the resource's request
DTO; DELETE removes where permitted. Do not assume a POST is replay-safe, or that a PUT accepts
every response field. `Patchable<T>` represents absent/null/value on supported partial updates.

Common statuses are 200/201/204 for success, 400 for validation, 401 for missing authentication,
403 for insufficient authority, 404 for absent or hidden resources, 409 for state/conflict failures,
and 422 for domain validation. Exact mapper behavior governs. A foreign-owner resource often
returns 404, not a universal `tenant-mismatch` 403. Identity-management routes have their own
`tenant-mismatch` and `not-manageable` rules. An unavailable paid engine in a free build is distinct
from an installed engine rejecting entitlement.

429/502/503/504 are useful HTTP conventions, not proof of a universal rate-limit, retry,
maintenance or gateway layer. Clients must inspect the actual response and avoid blindly retrying
mutating actions.

## 3. Request and response format

Ordinary JSON resources declare `application/json`. CSV, PDF and ZPL download/print endpoints
have different media types. Resource-specific response DTOs are the wire contract: for example,
`DeliveryOrderResponse` has an integer `state` and `prio` and a nullable `orderStrategyId`, not an
embedded strategy object or a universal state-name string. Other APIs use enum names. Do not
infer one module's representation from another's.

Quantities use JSON numbers backed by `BigDecimal`; scale and validation vary by field. Instants
use ISO-8601 timestamps; date-only values use `YYYY-MM-DD`. Warehouse-local day calculations use
`WarehouseZone`, not an assumption that every business date is UTC.

## 4. Error handling (RFC 7807)

`libs/karyo-common/.../exception/ProblemDetail.kt` defines:

| Field | Type / behavior |
|---|---|
| `type`, `title`, `detail` | Strings supplied by the exception mapper |
| `status` | HTTP status integer |
| `instance` | Nullable request instance; not supplied by every mapper |
| `traceId` | Nullable; do not depend on it with tracing disabled |
| `timestamp` | Instant, defaulted when the response is created |

There is no extensible property bag or universal `violations` array in this DTO.
`ConstraintViolationExceptionMapper` returns 400 with type
`https://karyo.com/errors/validation-failed` and joins property-path/message pairs in `detail`.
Do not parse the prose into a structured field-error contract. Framework/proxy authentication and
routing errors may be produced outside the application mappers.

## 5. Pagination

Paginated endpoints consume `PaginationParams` and return `PaginatedResponse`:

```json
{
  "content": [],
  "page": { "number": 0, "size": 20, "totalElements": 0, "totalPages": 0 }
}
```

`page` is zero-based, default 0; `size` defaults to 20. `PaginationParams` has no maximum-size
validation, and stock-unit listing passes `size` directly to `Page.of`. The historical 100-row
maximum is an unimplemented convention, not an enforced cap; check each endpoint's validation.

`sort` is a list of `field,direction` parameters. `SortParser` only accepts the resource's allowed
fields, ignores unknown fields and falls back to the resource's default if none survive.
Omitted/non-`desc` direction is ascending.

Not all collections are paginated. `GET /api/v1/journals` returns a JSON array ordered by
`created desc`, with optional `productNumber`, `correlationId`, integer `recordType`, and
`location` (location **name**) filters. It has no cursor, limit or page contract. Some lookup and
action endpoints also return arrays, including pick-order creation. Cursor pagination was a
design example, not an implemented API.

## 6. Filtering and sorting

Each resource explicitly declares its filters. For example, stock-unit listing accepts
`itemDataId` and `unitLoadId`, plus pagination; use a synthetic item id from your own warehouse:

```text
GET /api/v1/stock-units?itemDataId=123&page=0&size=20&sort=created,desc
```

The previous examples of arbitrary `.gt`, `.like`, `.in` and cursor parameters described an
unimplemented generic query layer. They are not supported by adding suffixes to any field name.
Use the DTO/resource for state representation, accepted filter combinations and default sorting.
Unknown parameters are not evidence that a filter was applied.

## 7. API versioning

The deployed REST surface is v1. URL-major versioning and backwards-compatible additions are
the design convention. Additive fields should be optional/defaulted; consumers should tolerate
unknown fields and enum values. Removing/changing required fields or semantics needs an explicit
compatibility decision.

The earlier six-month deprecation window and `Sunset`/`Deprecation` examples are lifecycle policy
intent, not an implemented header mechanism or proof of a supported v2 API. Do not announce a
migration/support window without a release decision. Internal SPI compatibility is separately
covered by [extension versioning](extensibility-architecture.md#versioning-and-patch-safety).

## 8. Event schema standards

CDI payloads and HTTP webhook envelopes are different interfaces. CDI observers receive the event
class actually fired, not a universal `DomainEvent<T>` wrapper. The common envelope type exists
in `libs/karyo-events`; its existence does not wrap all notifications automatically.

The active webhook relay reads `outbox_events`, matches owner and event-type patterns, and sends
`WebhookEnvelope`. The [webhook catalog](../integration/webhook-event-catalog.md) owns exact event
names, payloads, signatures and retry semantics. Existing event types include `ItemDataCreated`
and `PickOrderReleased`; a reserved `karyo.*` topic convention is not their wire name.

There is no Kafka broker, partition-key ordering, dual-topic publication or JSON-Schema CI
validation here. Those were design proposals. External receivers should deduplicate by the stable
delivery id and verify signatures over raw bytes. A synchronous CDI observer instead participates
in the caller's transaction unless its `@Observes` phase explicitly changes that behavior.

## 9. OpenAPI specification

Generated OpenAPI and Swagger UI are unimplemented capabilities in the current assembly. Neither
the app/module builds nor the dependency catalog declares the SmallRye OpenAPI extension, so
`/q/openapi` and `/q/swagger-ui` are not available as development documentation endpoints. The
standard nginx proxy exposes `/q/health`, not those paths. A public production API portal and
CI-exported OpenAPI artifact are also not supplied.

Use the JAX-RS resources, API-module DTOs and contract tests to navigate the implemented surface.
For example, stock routes are owned by
[`StockUnitResource`](../../services/inventory-service/karyo-inventory-core/src/main/kotlin/com/karyo/inventory/api/v1/StockUnitResource.kt)
and their request/response shapes by
[`StockUnitDto.kt`](../../services/inventory-service/karyo-inventory-api/src/main/kotlin/com/karyo/inventory/api/dto/StockUnitDto.kt).
OpenAPI annotations and schema generation remain a proposed documentation convention, not the
current API contract; actual DTO serialization governs.

## 10. HATEOAS decision

Karyo does not use HATEOAS. Desktop and floor clients know their routes; there is no mobile BFF
or network call between domain services. Integrators use REST plus
[webhooks](../integration/webhook-event-catalog.md), not discovered `_links`.
